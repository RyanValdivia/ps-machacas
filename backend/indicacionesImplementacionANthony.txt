mplementación de pruebas no funcionales con Locust
Objetivo

Implementar todas las pruebas no funcionales definidas para el Hito 3 utilizando Locust (y scripts Python cuando sea necesario). Las pruebas deben reutilizar los endpoints existentes del sistema (no crear endpoints nuevos) y generar evidencias de ejecución.

Toda la implementación deberá ubicarse dentro de:

backend/tests/stress/

La estructura final esperada es:

backend/
└── tests/
    └── stress/
        ├── __init__.py
        ├── locustfile_pos.py          # NF-STRESS-01, 03 y 05
        ├── locustfile_inventory.py    # NF-STRESS-02
        ├── locustfile_volume.py       # NF-VOL-01
        ├── locustfile_soak.py         # NF-SOAK-01
        ├── seed_masivo.py             # generación de datos
        ├── report_pos.html
        ├── report_inventory.html
        ├── report_volume.html
        └── report_soak.html

Antes de implementar cualquier prueba, el agente debe inspeccionar el proyecto para identificar:

endpoints disponibles
autenticación requerida
modelos involucrados
estructura de productos
estructura de ventas
flujo de login
cómo crear correctamente una venta

No debe asumir nombres de campos.

Debe reutilizar el flujo funcional existente.

Prueba 1 — NF-STRESS-01 (Ventas Concurrentes)
Archivo
backend/tests/stress/locustfile_pos.py
Objetivo

Evaluar el rendimiento del endpoint de creación de ventas.

Escenario

Simular

50 usuarios concurrentes
duración: 2 minutos

POST /api/sales/ventas/

utilizando datos válidos.

Métricas

Registrar

Throughput
Latencia P95
Error Rate

Criterios

P95 ≤ 3 s
Error Rate < 5 %

Generar

Prueba 3 — NF-STRESS-03 (Race Condition)
Archivo
backend/tests/stress/locustfile_pos.py
Preparación

Crear un producto con

stock = 1
Escenario

Simular

10 usuarios concurrentes

Todos intentan comprar exactamente el mismo producto.

Validaciones

Debe comprobarse que

solamente 1 venta fue exitosa
9 ventas fueron rechazadas
respuesta HTTP 400 para las rechazadas
stock final = 0

Al finalizar ejecutar una consulta SQL para validar el stock.

Registrar el resultado.

Prueba 6 — NF-SOAK-01 (Soak Test)
Archivo
backend/tests/stress/locustfile_soak.py
Escenario

Simular

5 usuarios
duración: 30 minutos

Cada usuario ejecuta continuamente

login
búsqueda
venta

durante toda la prueba.

Métricas

Monitorear

Latencia P95
uso de memoria
estabilidad
crecimiento de memoria

Utilizar

docker stats

para monitorear el consumo de recursos.

Criterio

No debe existir crecimiento sostenido de memoria.

Generar

report_soak.html
Reportes requeridos

Cada prueba debe generar un reporte HTML mediante Locust.

Archivos esperados

report_pos.html
report_inventory.html
report_volume.html
report_soak.html
Evidencias requeridas

Cada prueba debe documentar:

Throughput (cuando aplique).
Latencia P95.
Error Rate (cuando aplique).
Número de Timeouts (cuando aplique).
Uso de CPU.
Uso de memoria.
Capturas de docker stats para las pruebas correspondientes.
Resultado de la consulta SQL que verifica el stock final en la prueba NF-STRESS-03.
Requisitos importantes para el agente

Antes de escribir cualquier prueba, el agente debe analizar el proyecto para identificar:

estructura del backend Django;
modelos de Productos y Ventas;
endpoints reales disponibles;
autenticación (JWT, Session, Token, etc.);
formato esperado del payload de cada endpoint;
datos mínimos necesarios para crear una venta válida.

No debe inventar endpoints, nombres de campos, modelos ni payloads. Todas las pruebas deben adaptarse a la implementación existente del proyecto.
